# 业务链路梳理

把一个具体业务场景解释为有源码证据的执行路径。默认使用简体中文，保留实际技术标识；用户只要某种视图或修改现有图时，集中交付该部分。

## 确定本次场景

从用户信息和仓库中提取入口、参数、相关代码位置、读者、追踪范围与输出位置。先定位源码再补问；只有缺失信息妨碍正确选择入口或场景时才提问。没有参数时可以输出带条件的全景，不能冒充某次请求的实际路径。

- 记录各仓库的路径、分支/提交和相关工作区修改；分析当前实际文件，不能用 HEAD 代替未提交的代码。非 Git 源码包用来源、文件清单与内容哈希标记基线。报告用行号证据，并标明分析基线。
- 保留原入参语义。对转义 JSON 可以规范化展示，但不能擅改字符串/数字、金额精度、空值、日期或标识。标明必要假设。
- 给出业务字段的源码含义，枚举编码不能凭字面猜测；数量字段明确计数对象，不能把订单数、摘要数和明细数混用。
- 本次授权是读取和解释链路；真实提交业务请求、触发消息、修改业务代码、性能压测不属于默认验证方式。

## 先建立证据，再写解释

用 `rg`、IDE 符号导航或可用源码工具定位入口，沿调用、实现绑定和数据变化向下追踪。历史文档是线索，关键结论回到当前源码核对。

枚举或实现位于依赖包时，可静态检查本地依赖源码、`javap` 或反编译结果；记录所核对的依赖版本、制品哈希和对应位置，区分源码与字节码证据。构建实际选用版本或生产部署版本无法确认时，明确这一限制。

维护简洁的分支表与证据索引；组织输出时使用 [报告模板](assets/report-template.md)。模板是完整报告的默认结构，按用户范围删减，不填充无意义空节。

分支结论分为：

- **入参可确定**：给出条件表达式、入参/枚举依据和选中的路径；未选路径简短说明跳过原因。
- **条件待定**：依赖数据库记录、配置、当前时间、RPC 返回或前序执行结果。画出必要条件或列为未知，不能自动假设成功、存在、到期、开关开启。
- **源码边界未闭合**：缺少实现、消费端、配置或依赖。说明最后确认到哪里、缺什么，不能根据接口名补出下游逻辑。

路径事实应写成“若前序校验通过，则执行……”。源码能证明调用与条件，不能证明某次生产请求已成功执行；实际轨迹需对应日志、trace 或数据佐证。文档中将源码确认、推断、运行证据明确区分。

## 跨越每种执行边界

针对链路实际出现的边界，读取 [取证与交付检查](references/evidence-and-diagrams.md)：

- **普通方法**：追到改变业务条件、数据、状态或执行顺序的方法；简单 getter/日志辅助可合并列出。概览到方法级，详情解释每个纳入链路的方法做了什么。
- **RPC/HTTP**：调用方、目标系统、接口方法、DTO 关键转换、返回校验和失败行为；有下游源码时继续追。接口声明不是实现证据。
- **MQ/事件**：生产点、实际传输方式、topic/tag/key 的值或表达式、消费者绑定、消费逻辑、确认/重试/去重；无法证实的机制标为未知。不要把名叫 Provider 的方法一律画成 MQ。
- **异步/并发/分片**：提交点、执行器、分片对象和大小依据、每片工作、是否等待、汇总点、异常是否传播、返回与完成的关系。外层同步不代表内层同步，捕获异常后继续也不等于全部成功。
- **定时/延时/回调**：注册条件、业务时间与执行时间、时区/日期比较、载荷、入口、重查状态、竞争条件。始终把触发链与之后的处理链连接起来；定时条件不能用原请求时间代替当前时钟。
- **持久化/事务**：关键表、读写条件、状态前后值、条件更新及影响行数的处理。只有证据支持时才描述事务、锁、幂等和回滚范围；线程或网络边界不能自动继承本地事务。

默认追到本次业务结果、异步回流及有意义的外部边界。优先展开影响本次分支、状态和返回的方法，基础设施只保留支撑结论的必要证据；无关后续业务列为范围外。不要因入口方法返回就停止。存储细节是否省略由本次目标决定，不固定排除某个系统。

## 交付两种阅读深度

1. **概览**：先一句话解释场景与整体结果；方法级表格每个方法用一小段话描述作用；面向外部读者的系统图显示谁调用谁的什么接口、谁给谁发什么消息，以及接收后的关键处理。
2. **详细**：按真实执行关系解释关键方法的输入与转换、查询/校验、写入/状态、分片/并行、外部调用、返回与异常。引用证据编号避免重复贴长代码。顺序、条件和并行关系与概览一致。

若“系统交互”和“内部方法细节”放在一起过密，分别绘制系统时序图和局部活动/分片图，沿用节点编号。简单链路可以一张图充分表达；不要为了凑图重复内容。

优先用可维护的图源（如 Mermaid 或现有 draw.io 文件）。沿用用户已有格式；新增图保存可编辑源与可阅读成品。使用可用的渲染/预览工具检查成品，不能以语法通过替代视觉检查。没有可用工具时明确交付为未完成视觉验证的图源，不宣称成品通过验收。

## 完成前核对

- 分支、方法、图中的每条重要交互均能追溯到证据；未确认条件没有被写成必然。
- 分片、并行、返回边界、异常、延时消息与消费回流在对应视图中完整；失败路径按影响展开，不把所有可能故障混成主路径。
- 系统归属、调用方向、接口/消息标识、状态含义相互一致；不要在图里新增文字报告未证实的事实。
- 每张图逐项目视检查：线不穿过组件内部；箭头明确且不遮挡；没有两条及以上完全重叠的线；标注文字不与线条重叠。时序图另查生命线覆盖所有交互、阶段背景对齐、长文本不截断。参与方自身的处理用标准自调用或内部处理注释表达。
- 发现图形问题先修复再交付，并简述修正项；没有实际渲染/检查不能声称通过。
- 最终提供结果路径、主要结论和未闭合边界；说明是静态分析还是带运行证据的验证。仅写完模板不代表链路已验证。
