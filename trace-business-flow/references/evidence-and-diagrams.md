# 取证与交付检查

用于跨系统、异步、分片或制图任务；按本次出现的机制选择检查，不要求每条链路包含全部机制。

## 证据记录

建议使用 E01 等证据编号，记录仓库、文件、方法、有效行号和支持的具体结论。最终本地文件链接使用绝对路径；为跨机器迁移可同时保留仓库相对路径与提交号。引用必须支持当前结论，不能只链接一个几千行文件的开头。

同时核对调用点与被调实现。接口有多个实现时查注入、注册、路由和运行配置；绑定缺失时列出候选，不任挑一个。跨仓库版本无法匹配部署时，说明只是这些源码快照之间的关系。

参数来自用户时称为“给定输入”，日志或测试记录来自运行时才称为“观测结果”。把日志里的方法名当线索，不把“发送成功”的日志自动解释成对端完成。

## 容易误读的边界

| 观察到的代码 | 继续确认 | 不可直接推导 |
|---|---|---|
| `provider.publish(...)` | 分支内部究竟 RPC、MQ 还是本地调用；开关来自哪里 | 名称含 publish 就必然异步 |
| `submit` / `runAsync` / `parallelStream` | 执行器、拒绝策略、join/get、异常处理、返回时点 | 每片成功、全局事务、无限并行 |
| `allOf(...).join()` | 子任务是否吞异常、异常返回值是否检查 | join 返回即全部业务成功 |
| `@Transactional` | 实际调用是否经过代理、事务资源和线程边界 | 私有/自调用/新线程或 RPC 都在同一事务 |
| `update...` | WHERE 条件、版本与影响行数、调用方处理 | 返回未抛异常即更新成功 |
| 延时发送/日终定时 | 触发谓词、时钟与时区、消费者重新判断 | 提交时间就是截止时间，消息到达就一定关闭 |
| 分页或分片 | 稳定排序、集合来源、每片范围、汇总方式 | 分页天然等于一致快照，分片天然防重 |
| 状态码或布尔值 | 枚举、调用点、转换/覆盖 | 同名字段在不同系统语义相同 |

没有相关实现就将该项标为未知；检查单不是要求补造机制或自动开展架构整改。

## 图形表达

### 系统交互图

- 参与方代表实际系统；需要解释内部逻辑时以方法名注释或局部细节图表达，避免把每个 Java 类当系统。
- 标明 RPC、MQ、进程内异步等真实边界，不单凭实线/虚线让读者猜。
- 调用箭头写接口/方法；消息写实际已知的 topic/tag 或配置表达式与业务事件。不泄露无关载荷。
- `alt/opt` 展示关键条件，`loop` 展示分片，只有源码确认并行才用 `par`。标注谁等待、等待什么，入口返回后仍执行的任务另起阶段。
- 把“已受理”“发送完成”“消费者处理完成”“业务成功”分开表达；跨通道没有顺序保证时，不画成有保证的全序。
- 未取得消费者源码时，画到消息边界或明确标为未核对的外部参与方，不绘制想象的内部步骤。

### 方法与分片细节图

- 节点用方法或业务动作命名，边带条件；重试、异常退出和汇总不要与成功流程混线。
- 大循环表达为一片/一次迭代及其范围，给出 `ceil(N / size)` 等有源码依据的公式；N 和配置值未知时保持符号，不能凭请求中的另一种数量代入。
- 核心控制点可用 M01 等编号与方法概览和证据表对应，减少重复长文本。

### 渲染验收

先渲染，再检查整图和文字密集区域。语法校验、节点/边统计只能辅助发现问题，不能证明布局通过。

Mermaid 可用 [渲染配置](../assets/mermaid-config.json) 作为起点：镜像底部参与方以延长生命线，浅色注释背景，消息标签白色描边遮开经过文字的生命线。通过 CLI 使用时传入 `-c`；这是布局起点，仍需根据内容调整并目视检查。其他绘图工具采用等效的背景留白与布局，不强制迁移格式。

逐项记录通过/不通过/未验证：

1. 连接线不穿过无关组件内部。
2. 所有连接方向清晰，箭头可见且未遮挡。
3. 没有两条及以上完全重叠的连接线。
4. 文字与线条不重叠（标签有留白/背景，不被线划过）。
5. 时序图生命线覆盖全部交互；阶段背景边界对齐；字体可读且无截断。
6. 代码、报告和图的条件、顺序、同步/异步与返回边界一致。

修正可采用缩短标签、增加留白、调整布局或拆图。调整后重新渲染检查。工具受限时如实报告未验证项；不能绕过验证后把图称为最终成品。
